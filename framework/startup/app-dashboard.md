# App Dashboard Skill

Every web app, REST API, and MCP server created through `nci-startup` gets the same two read-only endpoints:

| Route | Returns |
|---|---|
| `GET /dashboard` | A self-contained HTML page for people |
| `GET /api/dashboard` | The JSON document the page renders, for tools and the NCI Skills Registry |

The page and API always agree because the page only renders what `/api/dashboard` returns.

The page has these sections, in order: **At a glance** (status badge, release, and the live checks run for that page load, side by side), **Operational Status**, **Delivery** (current deployment and recent deploy runs), **SDLC** (tests, documentation, issues), **Security & dependencies**, and **Usage**.

This skill does not apply to the local command-line script type (`hello-world-cli`), which has no HTTP surface.

## Template files

Copy these from `framework/startup/app-dashboard/` into the generated project. Do not rewrite them from memory; the templates are the tested implementation.

| Template | Copy to | Use for |
|---|---|---|
| `python/dashboard.py` | project root | Flask apps and APIs (`register_flask`), Python MCP servers (`register_fastmcp`) |
| `python/ops_status.py` | project root | Python apps: reads the probe's summary for Operational Status, and provides local sample data |
| `python/probe.py` | project root | Python apps on Cloud One: the scheduled uptime probe (a separate Lambda function) |
| `python/sam-dashboard-ops.yaml` | merge into `template.yaml` | Python apps on Cloud One: the probe's table, role, function and schedule |
| `python/tests/test_probe.py`, `python/tests/test_dashboard_snapshot.py` | `tests/` | Python apps: tests for the probe and the snapshot script |
| `node/dashboard.mjs` | project root | Express apps and APIs (`registerDashboard`). This is still the version 1 template: it has no Operational Status, so that section reads "Not available" |
| `dashboard.html` | project root, next to the module | All |
| `scripts/build_dashboard_snapshot.py` | `scripts/` | All |
| `dashboard.config.example.json` | `dashboard.config.json`, then fill in | All |

For Java or other runtimes, implement the same routes and the payload contract below by hand, and reuse `dashboard.html` unchanged.

## Payload contract (schemaVersion 1)

`GET /api/dashboard` returns HTTP 200 with `Cache-Control: no-store` and these top-level keys:

- `schemaVersion`: integer, currently `1`.
- `generatedAt`: ISO 8601 UTC time.
- `app`: `id`, `name`, `description`, `version`, `owner`, `repository`, `appType`, `skillsUsed`.
- `health`: `status` (`ok` or `degraded`), `checkedAt`, `checks[]` of `{name, status, detail}`.
- `runtime`: `startedAt`, `uptimeSeconds`, `language`, `framework`.
- `usage`: `scope`, `since`, `totalRequests`, `errorRequests`, `byRoute`, `lastRequestAt`.
- `deployment`: `environment`, `stackName`, `region`, `commit`, `builtAt`, `workflowRunUrl`.
- `tests`: `ranAt`, `summary {total, passed, failed, skipped}`, `cases[] {suite, name, status}`.
- `documentation`: `items[] {title, path, url}`.
- `issues`: `open`, `fetchedAt`, `titlesIncluded`, and `items[] {number, title, url, labels}` when titles are included.
- `templateVersion`: integer, currently `2`. It tells tools which dashboard template an app runs.
- `sampleData`: `true` only when the app runs locally with `DASHBOARD_SAMPLE_DATA` set; otherwise `false`.
- `summary`: `status` (`ok`, `attention`, `degraded`, or `unknown`), `reasons[]`, and `lastDeployedAt`.
- `operations`: Operational Status from the scheduled probe: `checkedAt`, `ageSeconds`, `stale`, `probe {intervalMinutes, lastCheck}`, `uptime` and `requests` for the `24h` and `7d` windows, and `hourly24h[]`.
- `deploymentHistory`: `fetchedAt` and `items[]` of recent deploy-workflow runs.
- `dependencies`: `totalAlerts`, `fetchedAt`, and the `dependabot` and `pipAudit` findings.

Each `health.checks[]` item may also carry a `description` saying, in plain words, what the check covers.

A block whose data does not exist is `{"status": "unavailable", "reason": "<why>"}`. A block that cannot exist in the current environment, such as deployment data for a locally running app, is `{"status": "not_applicable", "reason": "<what it is and why it does not apply>"}`; the page shows it as "Not Applicable". Never fill a block with a guess, a placeholder, or a sample value, except the explicitly flagged local sample data described below. `usage` is counted in memory per running instance, so on Lambda it resets on cold start and covers only that instance; the `scope` field says so. Do not describe it as a global total.

Status meanings: **Operational** means every check the dashboard can see passes. **Needs attention** means the service answers but something is outside its target. **Degraded** means a health check is failing. **Unknown** means monitoring data is missing, stale or unreadable; it does not mean the app is broken.

## Operational Status: what uptime means for a Lambda

A Lambda function is not a server that stays running, so "time since start" is not availability. Availability is the share of scheduled health checks that passed. `probe.py` is a separate Lambda function that runs on a schedule (hourly by default), calls the app's `/health`, records the result as the CloudWatch metric `NCI/AppDashboard` `HealthCheckSuccess`, reads the app's Function URL metrics (requests, 4xx and 5xx, p95 latency, errors, throttles), and writes one summary item to a DynamoDB table. The running app only reads that item (`ops_status.py`), so it never calls CloudWatch. Summaries older than three missed runs are marked stale and the badge becomes Unknown.

Choose the schedule with the project owner. Hourly is the default because most NCI apps are used rarely; a shorter interval gives faster outage detection but many more calls to the app. The interval lives in `INTERVAL_MINUTES` in `probe.py`, the schedule in the SAM fragment, and the stale limit in `ops_status.py`; keep them consistent.

## Local sample data

Locally there is no probe, so Operational Status reads "Not Applicable". To review the page with made-up numbers, run the app with `DASHBOARD_SAMPLE_DATA=healthy` (or `attention`, `degraded`, `stale`). The page then shows a SAMPLE DATA banner above everything, because the Operational Status numbers, the status badge and its reasons are all derived from sample values. The setting is ignored whenever `AWS_LAMBDA_FUNCTION_NAME` is set, so deployed apps can never show sample data.

## Where each section's data comes from

Runtime values (`health`, `runtime`, `usage`) are computed live. Everything else is a build-time snapshot, `dashboard-data/snapshot.json`, produced by `scripts/build_dashboard_snapshot.py`. This keeps the running app free of GitHub tokens and outbound calls.

| Section | Source | When missing |
|---|---|---|
| Deployment | `GITHUB_SHA`, `GITHUB_RUN_ID`, `STACK_NAME`, `AWS_REGION`, `ENVIRONMENT` in CI | `unavailable` for local builds |
| Test cases | JUnit XML at `dashboard-data/junit.xml` | `unavailable` until tests are run with JUnit output |
| Documentation | `README.md` and `docs/**/*.md`, linked to the repository at the built commit | `unavailable` |
| Outstanding issues | GitHub Issues API for the repository in `dashboard.config.json` | `unavailable` |

JUnit output commands: `pytest --junitxml=dashboard-data/junit.xml`, `mvn --batch-mode verify` (copy `target/surefire-reports/*.xml` content into one file or point the script at the merged report), or `node --test --test-reporter=junit --test-reporter-destination=dashboard-data/junit.xml`.

## Workflow

1. Confirm the app type is web app, REST API, or MCP server. Skip this skill for the CLI type.
2. Copy the templates listed above. Create `dashboard.config.json` from the example using the values already collected during startup (name, description, owner, repository, version, app type, skills used). Do not ask the user again for values they already provided.
3. Wire the routes into the app:
   - Flask: `import dashboard, ops_status` then `dashboard.register_flask(app, health_checks=..., operations=ops_status.make_reader())` after `app = Flask(__name__)`. Give `health_checks` a function that checks the app's real dependencies (a data store it reads, an upstream service) and returns items with `name`, `status`, `detail`, and a plain-words `description`; make `/health` perform the same checks and return HTTP 503 when one fails, because the scheduled probe calls `/health`.
   - Express: `import { registerDashboard } from "./dashboard.mjs"` then `registerDashboard(app)` before the other routes.
   - Python MCP server: `dashboard.register_fastmcp(mcp)`, wrap each tool function with `@dashboard.track_tool("<tool name>")`, and serve over the streamable HTTP transport. The routes are plain HTTP routes, not MCP tools, so the "exactly one tool" baseline is unchanged. Over stdio there is no HTTP surface, so verify the dashboard with the HTTP transport.
4. Add a `tests/` test that fetches `/api/dashboard` and checks `schemaVersion == 1`, `health.status == "ok"`, and that `GET /dashboard` returns HTML. Run the tests with JUnit XML output into `dashboard-data/junit.xml`.
5. Run `python scripts/build_dashboard_snapshot.py`, start the local server, and open `http://localhost:<port>/dashboard` in the integrated browser. Never verify with `file://`. Confirm every section renders either data or an explicit "Not available" line, and that no `{{` placeholders appear.
6. Verify the JSON with `curl -sf http://localhost:<port>/api/dashboard` and confirm the keys above.
7. Include the dashboard URL and API URL in the project summary. Keep the page open until the user verifies it, as with the Hello World gate.
8. For cloud deployment, follow the dashboard steps in the Cloud One deployment foundation: run the snapshot script in the deploy workflow before `sam build`, smoke-test `/dashboard` and `/api/dashboard`, and record `dashboardApiUrl` in the registry entry. Python apps on Cloud One also merge `python/sam-dashboard-ops.yaml` into `template.yaml`, so the probe is deployed with the app.

## Existing projects: install or upgrade

Run this when `nci-startup` is invoked inside a project that already exists (the user answered "Existing project", or the working directory already holds an application). Do not ask for details the project already shows; inspect it first.

1. **Check eligibility.** Web app, REST API, or MCP server only. Skip local command-line scripts. Find the framework (Flask, Express, Python MCP, other), the entry point that creates the app, the test runner, and, if deployed, the SAM template and deploy workflow.
2. **Detect the installed state.** Look for `dashboard.py` or `dashboard.mjs`, and read `DASHBOARD_TEMPLATE_VERSION` (Python) or `/api/dashboard` `templateVersion`:
   - No dashboard files: **install**.
   - A dashboard without `DASHBOARD_TEMPLATE_VERSION`: version 1, **upgrade**.
   - `DASHBOARD_TEMPLATE_VERSION` below the library's: **upgrade**.
   - Same version: **verify only**; run the checklist and report.
   - A `/dashboard` or `/api/dashboard` route the project wrote itself (no template markers): stop and ask the user whether to replace it or keep it and report the contract gaps.
3. **Show the plan first.** List the files to be added or replaced and the routes and resources to be added. State that existing routes, including `/health`, are not changed, and get the user's confirmation before editing a project they did not just create.
4. **Work additively.** Add or replace only the template files and the single registration call, and leave other project code alone. For an **upgrade**, replace the template files wholesale (the templates are generated code), keep `dashboard.config.json` and any `health_checks` function the project wrote, and add `ops_status.make_reader()` as the new argument. Merge, never overwrite, the project's `template.yaml`, deploy workflow, and test files.
5. **Make `/health` meaningful.** If `/health` only returns a constant, add a real dependency check to it and to `health_checks`, with plain-words descriptions. This is the one behavior change to `/health`: its success response stays HTTP 200 with the same body keys, and it returns HTTP 503 only when a dependency fails. Say so in the plan.
6. **Wire the deploy.** If the project deploys to Cloud One, merge `python/sam-dashboard-ops.yaml`, add `OPS_TABLE` and the `ops-status-read` policy to the app function, and add the workflow permissions and the dependency-audit step described in the Cloud One deployment foundation. If it does not deploy to Cloud One, skip the probe and leave Operational Status as "Not Applicable".
7. **Test locally first.** Run the project's tests with the new probe and snapshot tests, run `python scripts/build_dashboard_snapshot.py`, start the app, open `/dashboard` in the integrated browser, and use `DASHBOARD_SAMPLE_DATA` to review Operational Status. Confirm the project's existing tests and routes still pass. Do not deploy until the user has reviewed the local page.
8. **Deploy only on request.** Run the workflow as a dry run, review the change set (it should add the table, role, function, and schedule and modify the app function), then the real deployment, then the smoke tests and registry update from the Cloud One deployment foundation. The probe's first report arrives within one schedule interval; until then Operational Status shows Unknown.
9. **Record what changed.** Tell the user which files were added or replaced, that `skillsUsed` in `dashboard.config.json` now lists `app-dashboard`, and that `dashboardApiUrl` was set (or why not).

## Registry link

After a successful deployment, the registry entry gets `dashboardApiUrl`, the absolute HTTP(S) URL of `/api/dashboard` for the deployed environment. The NCI Skills Registry reads it to show a live summary per application. Set it only after the deployed URL returned HTTP 200 with a valid payload. For local-only or undeployed apps, omit the field.

## Required Guardrails

- Read-only and unauthenticated routes expose only the payload above. Do not add environment variables, hostnames, IP addresses, file paths, stack traces, request bodies, headers, query strings, user identifiers, or credentials.
- `/api/dashboard` sends `Access-Control-Allow-Origin` for `https://cbiit.github.io` only (the Registry site), never `*`, so other websites cannot read it from a user's browser.
- Count requests by route template (for example `/items/<id>`), never by raw URL. Do not record user data.
- Insert every value into the page with `textContent`, never `innerHTML`. Only `http:` and `https:` links are rendered.
- Issue titles are included only when the GitHub repository is public. For a private repository, include the count and set `titlesIncluded` to `false`. Do not include issue bodies or comments.
- If the app's audience is not `public` or `nci-wide`, or its data sensitivity is `pii-phi`, keep the dashboard but tell the user it is reachable by anyone who can reach the app, and confirm before deploying.
- Do not put tokens in the snapshot, config, or workflow. In CI use only the automatic `GITHUB_TOKEN` with read access to issues. Never request or store a personal access token.
- Do not invent test results, issue counts, or deployment facts. Use `unavailable`.
- Do not over-engineer: the running app makes no outbound calls and starts no background threads. Its only AWS call is one `GetItem` of the probe's summary. The probe is a separate function that stores only numbers and timestamps, never URLs, hostnames, request data or credentials, and its role is limited to writing the `NCI/AppDashboard` metric, reading metrics, and writing one table.
- Sample data (`DASHBOARD_SAMPLE_DATA`) is for local review only, must set `sampleData` to `true` and show the SAMPLE DATA banner, and must be ignored when `AWS_LAMBDA_FUNCTION_NAME` is set.
- In an existing project, change nothing outside the template files, the one registration call, and the merged deployment additions, and never remove or alter existing routes.

## Quality Checklist

- [ ] `/dashboard` and `/api/dashboard` both return HTTP 200 locally.
- [ ] `schemaVersion` is `1`, `templateVersion` matches the library template, and every section is present, populated, `unavailable`, or `not_applicable` with a reason.
- [ ] `/health` still returns HTTP 200 when healthy and the same body keys.
- [ ] `/health`, `/dashboard`, and `/api/dashboard` are excluded from usage counts.
- [ ] A dashboard test exists and its result appears in the Test cases section.
- [ ] No secrets or sensitive values appear in the payload or snapshot.
- [ ] Locally, Operational Status reads "Not Applicable", and with `DASHBOARD_SAMPLE_DATA` the page shows the SAMPLE DATA banner; with `AWS_LAMBDA_FUNCTION_NAME` set, sample data is ignored.
- [ ] For an existing project: the project's own tests and routes still pass, and the user confirmed the plan before files were changed.
- [ ] After deployment, both URLs return HTTP 200 on the deployed endpoint, the probe has reported at least once, and `dashboardApiUrl` is in the registry entry.
